# SSH 算法协商兼容性测试脚本

一条命令，把一台机器上 sshd 的**每一个算法组合**逐个跑通，输出结构化的协商/认证/执行三层结果。
用于摸清「某台老服务器到底还能跟哪些 SSH 客户端/算法对上话」。

脚本**自动识别运行环境**并套用对应的测试集，全程自动备份与恢复配置，
不需要你手工改 `sshd_config`。

> **这是给运维/安全/兼容性验证场景用的工具**，不是压测工具，也不做密码破解。
> 运行期间会临时放开 `PermitRootLogin` / `PasswordAuthentication`，请务必读完
> [安全须知](#安全须知) 再用。

## 它解决什么问题

换客户端、升 OpenSSH、做等保整改、或者对接自研 SSH 实现时，最常踩的坑是：

- 服务端支持的算法和客户端支持的算法**交集为空**，握手直接失败，但报错信息很难定位到底是哪一环；
- 某些算法**看起来协商成功，实际被静默降级**了（例如 SSH-1 下请求 `arcfour`，实际落到 `3des`）；
- 不知道服务端**到底有没有**某个算法，只能凭文档猜。

这个脚本把这些事变成一张可核对的表：**每个算法组合一条记录**，
明确告诉你协商结果、认证结果、命令执行结果分别是 PASS / FAIL / WARN 还是「压根没跑」。

**能力边界（先说清楚）**：

| 做 | 不做 |
|---|---|
| 逐个算法组合发起真实 SSH 握手并记录结果 | 不暴力破解、不探测密码 |
| 自动探测环境并选择对应测试集 | 不主动测试未覆盖的发行版（会明确拒绝并退出） |
| 自动备份/恢复 `sshd_config`，带崩溃自愈 | 不保证 `kill -9` / 断电后配置一定完好（见 [安全须知](#安全须知)） |
| 以服务端日志为准判定**实际落地**的算法 | 不修改被测客户端的实现 |

## 支持的环境

脚本内置 **4 个环境画像**，**全自动探测，不支持手动指定**：

| 画像 | 判定条件 | 典型系统 | 测试重点 |
|---|---|---|---|
| **`centos6`** | OpenSSH < 6.x + SysV/service | CentOS 6.10（OpenSSH 5.3p1） | SSH-2 遗留算法 + **SSH-1 协议**（含 3des/blowfish/arcfour 等） |
| **`openssh8`** | OpenSSH 8.x + systemd | AlmaLinux/Rocky 9、Ubuntu 22.04、Debian 12 | OpenSSH 8.x 特有算法（如 `curve448-sha512`/X448） |
| **`modern`** | OpenSSH >= 9.x + systemd | AlmaLinux 10 | 现代算法全集（AEAD / CTR / CBC / KEX / HostKey / MAC，含后量子 KEX） |
| **`openeuler`** | `/etc/os-release` 的 `ID` 为 `openEuler` | openEuler 24.03 | 国密算法专项 |

> **环境不在以上范围内时**，脚本**不会对系统做任何改动**，只打印诊断信息后退出。
> 这是刻意设计的：宁可不动，也不要在未知环境上改配置。

**运行前置条件**：

- `bash` **4.0+**（脚本用到关联数组），启动时即校验；
- **root 权限**（`--list` 除外）；
- 依赖命令：`ssh`、`sshd`、`ssh-keygen`、`awk`、`grep`、`sed`、`tr`、`cut`、`head`、`tail`、`stat`、`mktemp`、`date`、`cmp`；
- 可选命令：`pgrep`、`ps`（来自 `procps-ng`）。精简镜像常缺失 —— **缺失不影响运行**，
  脚本会自动回退到遍历 `/proc` 的实现；
- 可选命令：`crontab`（来自 `cronie`/`cron`）。仅影响 SysV 环境的**开机自愈**能力，
  **缺失时脚本降级为「无自愈模式」继续跑完**，不会中止。

## 快速开始

```bash
# 1. 下载（把 <user>/<repo> 换成实际仓库路径）
curl -O https://raw.githubusercontent.com/<user>/<repo>/main/test_ssh.sh
chmod +x test_ssh.sh

# 2. 先看看当前环境会被识别成什么、会跑哪些项（不改动系统，不需要 root）
./test_ssh.sh --list

# 3. 正式跑（需要 root）
sudo ./test_ssh.sh --auto
```

就这三步。`--auto` 是无人值守模式，全程自动完成。
想中途盯着看、或者需要**用外部客户端手工连进来测**，用默认的**手动模式**：

```bash
sudo ./test_ssh.sh          # 每项测试都会停下来等你触发/确认
```

### 只跑某一项

```bash
sudo ./test_ssh.sh --auto --only=3          # 按编号
sudo ./test_ssh.sh --auto --only=blowfish   # 按关键字（匹配测试项描述）
```

`--only` 的编号来自 `--list` 的输出，二者配合是排查单个算法问题最快的路径。

## 命令行选项

| 选项 | 说明 |
|---|---|
| *(无参数)* | **手动模式**（默认）。每项测试需手动触发/确认，适合配合外部客户端联调 |
| `--auto` | **自动模式**。使用本地 `127.0.0.1` 回环客户端自动触发，无人值守 |
| `--list` | 只列出当前环境识别结果与将要执行的测试项，**不改动系统**，**无需 root** |
| `--only=N` | 只运行编号为 `N` 的测试项，可与 `--auto` 组合 |
| `--only=keyword` | 只运行描述中包含 `keyword` 的测试项，可与 `--auto` 组合 |
| `--port=N` | 指定测试端口（默认 `22`），取值须为 `1-65535` |
| `--allow-remote` | 允许 sshd 在测试期间监听**非回环地址**（默认仅 `127.0.0.1`） |
| `-h`, `--help` | 显示帮助 |

**关于 `--allow-remote`**：默认情况下脚本强制 sshd 只监听 `127.0.0.1`，
即使临时放开了弱配置也不会暴露到外网。确有跨主机测试需求
（例如通过隧道让外部客户端连进来）时才显式加上它 —— 加之前请确认网络边界可信。

```bash
# 跨主机/隧道场景的典型用法
sudo ./test_ssh.sh --auto --port=2222 --allow-remote --only=3des
```

## 输出说明

**只有 1 个输出文件**，TXT 格式，测试过程中**同时**实时打印到终端。

- 默认落在**当前工作目录**；
- 文件名形如 `ssh_algorithm_test_<时间戳>_<随机串>.txt`；
- 权限 `600`（内容含服务端握手细节，做了收紧）；
- 若当前目录不可写，自动回退到 `/tmp`；
- 结束时终端会打印一行 `结果与详细日志：<路径>`，直接看那行即可。

> 注意：即使 `--list` 这类只读探测也会创建日志文件（用于记录环境识别过程），
> 只是内容很短、不会改动任何系统配置。

日志包含三部分：**环境/执行信息**（环境识别结果、依赖命令可用性、Profile 判定依据）、
**逐项详细结果**（每项的固定值 vs 实际值、各层判定、原因）、**汇总统计**。

### 报告长什么样

输出是一份**纯文本报告**，可直接 `cat`/`less`/发给同事。报告**末尾**有一块「结论摘要」，
不用翻上千行就能拿到判断：

```
============================================================
 结论摘要（先看这里）
============================================================
 环境      : CentOS release 6.10 (Final)
 画像      : centos6
 总测试项  : 44

 【实际执行】 34 项     【从未执行】 10 项（服务端不支持，预检阶段即判定，非失败）

 【真正通过】 34 项 / 实际执行 34 项 （通过率 100%）

 [OK] 无「已执行但未通过」的项 —— 服务端不支持的部分已全部排除在外
 [!] 需要关注：有 2 项降级/偏差告警，算法"能连"但实际落地值与请求不同（见明细）

 --------------------------------------------------------
 非 PASS 项一览（共 10 项）
 --------------------------------------------------------
 编号 结果        测试组                  原因
 --------------------------------------------------------
 #41  WARN          SSH-1 Cipher               SSH-1 实际使用 cipher 与请求不一致（降级）：…
 #42  WARN          SSH-1 Cipher               SSH-1 实际使用 cipher 与请求不一致（降级）：…
 --- 以下为"服务端不支持/从未执行"，属预期负结果，通常无需处理 ---
 #15  FAIL          SERVER-FILTER/UNSUPPORTED  Server Filter 判定为 UNSUPPORTED：服务器不支持该算法
 …
 --------------------------------------------------------
```

一览表**按「要不要管」分组**：先 WARN（需人工确认），再真失败，
最后一行分隔之后是「预期负结果，无需处理」——从上往下读，看到分隔线就可以停。

> **完整报告样例与逐字段解读**见 [`结果文件说明书.md`](结果文件说明书.md)（含 1744 行真实产物）。

## 结果字段怎么读

每一个测试项都会输出一组结构化字段。理解下面几个，基本就能读懂全部报告。

### 三层结果：协商 / 认证 / 执行是**分开**判定的

| 字段 | 含义 |
|---|---|
| `NR`（协商结果） | SSH 握手阶段，算法协商是否成功 |
| `AR`（认证结果） | 身份认证是否成功 |
| `ER`（命令执行结果） | 登录后能否真正执行命令 |
| `CPR`（客户端进程） | 本地客户端进程自身的退出状态 |
| `CR`（客户端诊断） | 客户端侧给出的诊断分类 |

**这是本脚本的核心设计**：算法协商成功 ≠ 认证成功 ≠ 能执行命令。
把它们分开判定，才能区分「算法不支持」和「环境/权限问题」——
混成一个「成功/失败」会让排查方向完全跑偏。

> 特别地，**算法结果不与 SSH 客户端退出码直接绑定**。
> 老旧客户端在某些算法上的退出码本身就不可靠，直接绑定会把结论带偏。

### `总体结果` 的取值

| 取值 | 含义 |
|---|---|
| `PASS` | 协商 + 认证 + 执行全部通过 |
| `FAIL` | 失败。请结合 `原因` 与 `CR` 判断是**服务端不支持**还是**真的有 bug** |
| `WARN` | 跑通了，但**存在需要人工关注的偏差**（最典型：算法被静默降级） |
| `UNKNOWN` | 证据不足，无法判定 |
| `SKIP` | 本次运行按条件跳过 |

### `服务端预筛` 与 `ER: NOT_RUN`

预检阶段若发现**服务端根本不支持该算法**，会标为：

```
服务端预筛     : UNSUPPORTED（服务端不支持）
协商结果 NR   : FAIL
命令执行结果 ER: NOT_RUN      ← 关键：从来没执行过
```

**`NOT_RUN` 不是失败，是「压根没跑」**。这类项目占 `FAIL` 的绝大多数，
但它们是**预期中的负结果**，不是脚本或环境的缺陷。
统计时建议把 `ER: NOT_RUN` 的项单独摘出来 —— 这样才能算出真实的通过率。

> 报告末尾的**结论摘要会自动帮你做这件事**：它把「实际执行」和「从未执行」分开计数，
> 并给出「真正通过率」与「真失败数」，不需要你手工统计。

### 为什么会有 `WARN`（重要）

举一个真实例子。在 CentOS 6（OpenSSH 5.3p1）上请求 SSH-1 的 `arcfour`：

- 客户端日志里到处是 `arcfour` 字样，看起来协商成功；
- 但服务端日志实际打印 `No valid SSH1 cipher, using 3des instead.` ——
  **`arcfour` 根本不是合法的 SSH-1 算法，实际落下的是 3des**。

如果只看客户端日志，这一项会被错记为 **PASS（假通过）** ——
这正是兼容性测试里最危险的结果：**报喜不报忧**。

本脚本改用**服务端权威日志**（`debug1: Encryption type: <cipher>`）判定实际落地的算法，
并把这种「请求值 ≠ 实际值」的情况如实标为：

```
总体结果   : WARN
客户端诊断 : NEGOTIATION_MISMATCH
原因       : SSH-1 实际使用 cipher 与请求不一致（降级）：
             请求 arcfour，服务端实际 3des（客户端报：No valid SSH1 cipher, using 3des instead）
```

> **原则：以服务端为准，宁可报 WARN，也不给假 PASS。**

## 安全须知

请完整阅读本节。这是本脚本最需要谨慎对待的部分。

### 会临时放开什么

测试期间脚本会临时设置：

```
PermitRootLogin yes
PasswordAuthentication yes
```

**默认强制 sshd 只监听 `127.0.0.1`**，因此默认配置下这些弱配置不会暴露到外网。
只有显式加了 `--allow-remote` 才会放开监听范围 —— 加之前请确认网络边界可信
（建议同时在防火墙上限制来源 IP）。

### 配置是怎么恢复的

- **每次只修改一个测试配置**，该项测试完成后立即恢复，不做批量改写；
- `trap` 覆盖 `INT` / `TERM` / `EXIT` —— 正常退出、`Ctrl+C`、`kill` 都会自动恢复；
- `sshd_config` 的每次写入都是「**写临时文件 → 校验通过 → 原子替换**」，
  任何时刻磁盘上的配置要么是上一个合法状态，要么是新的合法状态，**不存在写坏的中间态**。

### 崩溃自愈的边界

脚本按 init 系统自动选择自愈实现：

| 环境 | 机制 | 可靠性 |
|---|---|---|
| systemd | `sshd.service` 的 `ExecStartPre` drop-in 钩子 | 每次启动 sshd 前检查并恢复备份，覆盖 `kill -9` / 重启 |
| SysV（如 CentOS 6） | `crontab @reboot` 尽力而为的开机检查 | **不能**保证抢在 sshd 之前执行，只能做到「开机后尽快」 |

> `crontab` 缺失时自愈功能不可用，脚本会**打印警告并降级继续**，
> 结束时仍会正常恢复配置，并在汇总里明确标注「本次为无自愈模式运行」。

**仍需警惕**：`kill -9` / 断电 / 文件系统损坏等极端情况，**可能**让配置停留在测试状态。
因此建议：

- 运行前用防火墙临时限制 SSH 端口来源；
- 确保有**控制台 / IPMI 等带外访问**方式作为最后手段；
- 不要在无法物理接触的生产机上首次试跑 —— 先在测试机/容器里验证。

### 其他

- 需要 root 权限（除 `--list`）；
- 输出日志权限为 `600`，但仍建议自行检查内容是否含敏感信息再外发。

## 它是怎么工作的

```
┌─────────────────────────────────────────────────┐
│ 1. 环境识别                                      │
│    读 /etc/os-release + ssh -V + init 系统        │
│    → 命中 4 画像之一，否则只诊断不动作            │
├─────────────────────────────────────────────────┤
│ 2. 环境预检                                      │
│    逐条检查依赖命令，缺失给安装建议               │
│    安装崩溃自愈钩子（systemd drop-in / crontab）  │
├─────────────────────────────────────────────────┤
│ 3. 备份                                          │
│    备份 sshd_config，记录初始状态                 │
├─────────────────────────────────────────────────┤
│ 4. 逐项测试（每次只改一项）                       │
│    ① Server Filter 预检 —— 服务端不支持则 NOT_RUN │
│    ② 写入单项配置（临时文件 → 校验 → 原子替换）   │
│    ③ 重启/重载 sshd，发起真实连接                 │
│    ④ 采集客户端日志 + 服务端日志增量              │
│    ⑤ 三层判定：协商 NR / 认证 AR / 执行 ER        │
│    ⑥ 恢复配置                                    │
├─────────────────────────────────────────────────┤
│ 5. 汇总 + 恢复现场                               │
│    输出统计，恢复原始配置，清理自愈钩子           │
└─────────────────────────────────────────────────┘
```

**几个关键设计点**：

- **服务端日志才是权威**。实际落地的算法以 sshd 的 debug 输出为准，
  客户端日志只作辅助（见 [为什么会有 WARN](#为什么会有-warn重要)）。
- **客户端明确拒绝 ≠ 服务端失败**。客户端自己不支持该算法时标为
  `CLIENT_REJECTED` / `UNKNOWN`，不冤枉服务端。
- **「没取到证据」不等于「不匹配」**。日志形态导致某个值解析不到时，
  该项断言会被**跳过**（视为未知），而不是判成 FAIL。
- **SSH-1 单独处理**。SSH-1 没有算法协商报文，判定逻辑与 SSH-2 完全隔离，
  避免两套语义互相污染。

## 常见问题

**Q：`--list` 报了「环境识别失败」，怎么办？**

说明当前系统不在 4 个画像内。脚本**不会做任何改动**，这是预期行为。
输出里会列出支持的四类环境和当前探测到的信息，可据此判断是版本不匹配
还是缺少 `systemctl`/`service`。

**Q：`FAIL` 一大堆，是不是脚本有问题？**

先看每一项的 `服务端预筛` 和 `ER`：

- `Server Filter: UNSUPPORTED` + `ER: NOT_RUN` → **服务端不支持该算法，属预期负结果**，不是 bug；
- `Server Filter: NONE` 且 `ER` 是 `FAIL` → 这才需要深挖，结合 `原因` 字段分析。

**Q：提示缺少 `crontab` / `pgrep` / `ps` 会影响结果吗？**

不会。

- `pgrep`/`ps` 缺失 → 自动回退遍历 `/proc`，功能完整；
- `crontab` 缺失 → 仅开机自愈不可用，脚本降级继续，结束时照常恢复配置。

想消除提示：`yum install -y cronie procps-ng` / `dnf install -y cronie procps-ng` / `apt-get install -y cron procps`。

**Q：能测 Windows 上的 OpenSSH 吗？**

不能。画像判定基于 `/etc/os-release` 与 init 系统，Windows 不在覆盖范围。

**Q：跑到一半 `Ctrl+C` 了，配置改回来没有？**

会。`trap` 覆盖了 `INT`/`TERM`/`EXIT`。但请核对脚本输出末尾的恢复日志确认。
若是 `kill -9`，依赖自愈钩子（见 [崩溃自愈的边界](#崩溃自愈的边界)）。

**Q：想加自己系统的支持怎么办？**
